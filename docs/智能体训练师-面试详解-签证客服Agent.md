## 二、业务场景与产品目标

### 2.1 目标用户与问题

- **用户**：天猫/私域咨询签证的客户  
- **痛点**：重复问答（材料、周期、进度）、话术不统一、敏感承诺风险（保证出签）、人工成本高  
- **Agent 目标**：成为「初级签证客服 AI 员工」——能答公开政策、能引导材料、能查 Mock 进度、高风险必须转人工  

### 2.2 成功指标（面试可提）

| 指标 | 含义 |
|------|------|
| 一次解决率 | FAQ/材料类不转人工的比例 |
| 转人工准确率 | 该转的一定转（投诉/造假/保证出签） |
| 幻觉率 | 知识库无结果时是否仍编造政策 |
| 槽位追问完成率 | 缺国家/签证类型时是否先追问再答 |
| 红队 Pass | 诱导承诺出签等必须拦截 |

### 2.3 输入 / 输出契约

- **Graph 输入**：`{ "user_message": "用户原话" }`  
- **Graph 输出（核心）**：`final_reply`，以及 `intent` / `risk_level` / `need_handoff` / `handoff_reason` 等状态字段

## 三、总体架构（系统思维）

### 3.1 设计原则（对标 JD「系统思维」）

1. **先分流，再执行**：意图决定走哪条业务流水线  
2. **先齐信息，再检索**：材料类「槽位 → 知识库」，避免空检索乱答  
3. **工具结果可信**：进度只来自插件，查无不编造  
4. **风控盖全链路**：除闲聊直达外，业务路径最终都进风险门控  
5. **权限显式化**：用 `flow_path` 告诉回复节点「这一轮该追问 / 确认 / 正常答 / 转人工」  
6. **红线进提示词 + 进规则节点**：双保险，不单靠 LLM  

### 3.2 技术分层

| 层 | 内容 |
|----|------|
| 编排层 | LangGraph `StateGraph`（`graphs/graph.py`） |
| 状态层 | Pydantic `GlobalState`（会话黑板） |
| 智能层 | LLM 节点：意图 / 槽位 / 回复（Coze `LLMClient`） |
| 知识层 | `KnowledgeClient` 语义检索 `visa_knowledge` |
| 工具层 | Mock 订单进度插件 |
| 规则层 | 投诉转人工、订单号校验、风险关键词门控 |
| 交互层 | 静态 H5 →（需国内可访问代理）→ `/run` |

### 3.3 与你个人技术栈的「翻译句」（面试高频）

| 你已掌握 | 在本项目中的对应 |
|----------|------------------|
| LangGraph | 主图编排、条件边、状态流转 |
| Python | 全部节点实现 |
| Spring 全家桶 / Spring AI Alibaba | 可类比：后端编排 + ChatClient + Function Calling；本 Demo 用 Coze LLM/知识库能力等价落地 |
| Coze | Coding 工作流、知识库、部署 `/run` |
| Cursor | 迭代节点、修 messages 格式、写 H5/代理 |

> 面试金句：  
> 「Coze 工作流画布 ≈ LangGraph；插件/工具 ≈ Spring AI Function Calling；知识库 ≈ RAG。」

## 四、全局状态（Agent 的「工作记忆」）

面试官若问「Agent 和 Chatbot 差别」，可答：我们用显式状态，而不是只靠多轮聊天记录。

| 字段 | 类型 | 谁写入 | 用途 |
|------|------|--------|------|
| `user_message` | str | 入口 | 原始用户话 |
| `intent` | str | 意图分类 | faq/material/progress/complaint/chitchat |
| `country` / `visa_type` | str | 意图分类 / 槽位填充 | 检索与清单 |
| `order_id` | str | 意图分类 / 订单校验 | 查进度 |
| `missing_slots` | list | 槽位 / 知识库材料分析 | 追问或列材料 |
| `slot_follow_up` | str | 槽位填充 | 追问话术 |
| `order_valid` | bool | 订单校验 | 是否允许调插件 |
| `order_follow_up` | str | 订单校验 | 无号/格式错误提示 |
| `order_status` | str | 进度查询 | 插件结果文本 |
| `knowledge_context` | str | 知识库检索 | RAG 上下文 |
| `need_handoff` / `handoff_reason` | — | 投诉 / 风控 | 转人工 |
| `complaint_summary` | str | 投诉节点 | 给人工的结构化摘要 |
| `risk_level` / `risk_advice` | — | 风控 | low/medium/high |
| `need_confirm` / `confirm_prompt` | — | 风控 | 中风险确认 |
| `flow_path` | str | 意图(闲聊) / 风控 | ask/confirm/normal/handoff/chitchat |
| `final_reply` | str | 回复生成 | 对用户最终话术 |

### 节点 1：`intent_classify`（LLM 意图分类）【Agent 节点】

| 项 | 说明 |
|----|------|
| **文件** | `nodes/intent_classify_node.py` |
| **配置** | `config/intent_classify_llm_cfg.json` |
| **类型** | 大模型节点（低温度，偏确定性） |
| **干什么** | ① 把用户话分到 5 类意图；② 抽取 `country` / `visa_type` / `order_id`；③ 闲聊时直接写 `flow_path=chitchat` |
| **为什么需要** | JD 要求「意图理解」；后续所有分支依赖此结果。分类错了，整条流水线都会错。 |
| **五类意图** | 见下表 |
| **输出 JSON** | `{intent, country, visa_type, order_id}` |
| **异常** | JSON 解析失败 → 默认 `chitchat`，避免误入业务；intent 非法值同样兜底 |
| **工程细节** | 调用 LLM 时使用 `role/content` 纯文本 messages，避免 Coze 网关 `dict has no attribute name` |
| **对标 JD** | Prompt 调优、结构化输出、场景训练 |

**意图定义与优先级（背下来）：**

| intent | 含义 | 典型话术 | 优先级 |
|--------|------|----------|--------|
| `complaint` | 投诉/退款/保证出签/造假等 | 「保证出签吗」「我要退款」「假在职」 | **最高** |
| `progress` | 查订单进度 | 「查 VISA-001001」 | 次高 |
| `faq` | 政策/周期/怎么办 | 「日本签要多久」 | 普通 |
| `material` | 材料清单 | 「英国旅游签要什么材料」 | 普通 |
| `chitchat` | 问候/无法归类 | 「你好」 | 兜底 |

**分类优先级规则（写在 System Prompt 里）：**  
投诉类关键词命中 → 必须 `complaint`；有订单号/查进度 → `progress`；「要多久/政策」→ `faq`；「要什么材料」→ `material`。

---

### 条件边 A：`route_by_intent`（意图路由）

| 项 | 说明 |
|----|------|
| **干什么** | 根据 `intent` 选下一条流水线 |
| **映射** | complaint→投诉转人工；chitchat→直接回复生成；progress→订单校验；faq/material→槽位填充 |
| **对标 JD** | 「完整任务流」而不是一个万能 Prompt |

---

### 节点 2：`complaint_handoff`（投诉转人工）【规则任务节点】

| 项 | 说明 |
|----|------|
| **文件** | `nodes/complaint_handoff_node.py` |
| **干什么** | 敏感场景**不靠模型软劝**，用关键词识别原因，生成结构化摘要，强制 `need_handoff=true`，`flow_path=handoff` |
| **为什么做成规则** | 「保证出签」「造假」等若交给生成式模型，容易嘴软或越权；规则节点可控、可审计 |
| **输出** | `need_handoff`、`handoff_reason`、`complaint_summary`（含意图/国家/原因/原话摘要） |
| **下一跳** | → `risk_assessment`（全链路风控仍覆盖） |
| **对标 JD** | 行为边界、转人工策略、异常/合规路径 |

**关键词示例：** 保证出签、退款、投诉、造假、假材料、做假、加急保证…

---

### 节点 3：`slot_filling`（槽位填充）【Agent 节点】

| 项 | 说明 |
|----|------|
| **文件** | `nodes/slot_filling_node.py` |
| **配置** | `config/slot_filling_llm_cfg.json` |
| **干什么** | 检查业务必填槽位是否齐全；缺失则用 LLM 再提取或生成追问话术 |
| **必填策略** | `faq` 需要 `country`；`material` 需要 `country` + `visa_type`；progress/complaint/chitchat 不在此强依赖 |
| **设计意图** | **材料类「先槽位后检索」**——用户只说「我想办签证要什么材料」时，先问国家与类型，再查清单，避免瞎答 |
| **输出** | 更新后的 country/visa_type、`missing_slots`、`slot_follow_up` |
| **对标 JD** | 多步任务、信息收集、工作流优化 |

### 条件边 B：`route_after_slot_filling`

| 结果 | 下一跳 | 含义 |
|------|--------|------|
| 仍有 `missing_slots` | → `risk_assessment` | 走追问路径（ask），仍过风控 |
| 槽位齐全 | → `knowledge_retrieval` | 可以检索知识库 |

### 节点 4：`knowledge_retrieval`（知识库检索）【任务节点】

| 项 | 说明 |
|----|------|
| **文件** | `nodes/knowledge_retrieval_node.py` |
| **干什么** | 用国家/签证类型/意图拼 query，调用 `KnowledgeClient.search`，取 top_k 片段写入 `knowledge_context` |
| **知识库文档** | `countries_faq.md`、`material_checklist.md`、`risk_policy.md` → 数据集 `visa_knowledge` |
| **material 增强** | 检索后做材料清单提示（通用必备 + 按旅游/商务/学生类型补充），写入 `missing_slots` 供展示「还缺哪些材料」 |
| **异常** | 无结果或异常 → `knowledge_context=""`，交给回复节点明确说「暂未查到」，**禁止编造** |
| **对标 JD** | 知识库配置、RAG、防幻觉 |

**检索 query 构造逻辑（口述）：**  
国家 + 签证类型 +（material→「材料清单」/ faq→「签证政策」）+ 用户原话，去重拼接。

### 节点 5：`order_validate`（订单号验证）【规则任务节点】

| 项 | 说明 |
|----|------|
| **文件** | `nodes/order_validate_node.py` |
| **干什么** | 在查进度前保证有合法订单号；支持从整句提取 `VISA-\d+` |
| **三种结果** | ① 无号 → 追问话术，`order_valid=false`；② 格式错 → 提示正确格式；③ 合法 → `order_valid=true` |
| **为什么独立** | 避免无号就调工具、或模型编造进度 |
| **对标 JD** | 工具调用前置校验、异常路径 |

| 结果 | 下一跳 |
|------|--------|
| `order_valid=true` | → `order_progress_query` |
| 无效 | → `risk_assessment`（带 `order_follow_up` 追问） |

### 节点 6：`order_progress_query`（订单进度查询）【工具任务节点】

| 项 | 说明 |
|----|------|
| **文件** | `nodes/order_progress_query_node.py` |
| **工具** | `tools/order_progress_tool.py` → `query_order_progress` |
| **干什么** | 用已校验订单号查 Mock 库，拼成可读进度文本 |
| **Mock 数据** | 如 `VISA-001001` 审理中、`VISA-001003` 已出签、`VISA-001005` 已拒签等 |
| **异常** | `found=false` → 查无友好提示；异常/超时 → 致歉并建议人工；**绝不编造进度** |
| **下一跳** | → `risk_assessment` |
| **对标 JD** | 外部工具（API）集成、异常处理、结果返回 |

### 节点 7：`risk_assessment`（风险门控）【规则任务节点 · 关键】

| 项 | 说明 |
|----|------|
| **文件** | `nodes/risk_assessment_node.py` |
| **干什么** | ① 评 `risk_level`；② 决定是否转人工/是否需确认；③ **统一写出 `flow_path`** 给回复节点 |
| **覆盖范围** | 投诉、知识库、进度、追问等业务路径汇合点（闲聊除外，闲聊在意图节点已标 `chitchat`） |
| **对标 JD** | 「定义自主执行 / 用户确认 / 转人工」——本节点是权限中枢 |

**风险等级策略：**

| 等级 | 触发示例 | 行为 |
|------|----------|------|
| high | 造假、保证出签、包过、敏感背景等 | `need_handoff=true`，倾向 handoff |
| medium | 自由职业、流水不足、加急、明天出发等 | `need_confirm=true`，出确认问句 |
| low | 无明显风险词 | 正常回答 |

**`flow_path` 优先级（必背）：**

```text
handoff（转人工） > ask（缺槽位/缺订单号追问） > confirm（中风险确认） > normal（正常答复）
```

**为何「加急」放 medium 而不是 high：**  
加急诉求需要说明「不能承诺明天必出」，用确认节点让用户选择「确认继续 / 转人工」，比直接恐吓式转人工更符合客服体验；而「保证出签/造假」必须硬拦截。

---

### 节点 8：`response_generate`（回复生成）【Agent 节点】

| 项 | 说明 |
|----|------|
| **文件** | `nodes/response_generate_node.py` |
| **配置** | `config/response_generate_llm_cfg.json` |
| **干什么** | 综合状态与知识库/订单结果，生成对用户的自然语言回复 |
| **强制红线（System Prompt）** | ① 只依据知识库/插件，禁止编造；② 禁止出签承诺；③ 敏感证件号提醒；④ 政策免责声明 |
| **按 `flow_path` 策略** | 见下表 |
| **对标 JD** | Prompt 工程、场景话术、输出质控 |

**各 `flow_path` 回复策略：**

| flow_path | 策略 |
|-----------|------|
| `ask` | 优先追问（slot_follow_up / order_follow_up），可附风险提示 |
| `confirm` | 简要说明限制 + **必须附上确认问句**，不假装已办妥 |
| `normal` | 结论 → 依据要点（来自知识库）→ 下一步行动 |
| `handoff` | 投诉摘要 + 转人工话术，不承诺退款/出签结果 |
| `chitchat` | 短回复 + 引导回签证问题 |

**空知识库时：** 明确「暂未查询到」，引导官网或人工，而不是用模型参数记忆瞎答。

---

### 节点 9：结束（End）

返回 `GraphOutput`：`final_reply` 及意图、风险、是否转人工等，供前端展示标签或路由人工坐席。

## 六、三条主链路「走读」（面试演示口述稿）

### 6.1 FAQ 成功路径

**用户：**「日本旅游签一般要多久？」  

1. 意图 → `faq`，抽出 country=日本  
2. 槽位：faq 需国家 → 已齐  
3. 知识库检索日本政策片段  
4. 风控：低风险 → `flow_path=normal`  
5. 回复：按知识库说明周期 + 免责声明  

**你要强调：** 答案可追溯到知识库，不是模型瞎编。

### 6.2 材料追问路径

**用户：**「我想办签证，要准备什么？」  

1. 意图 → `material`，国家/类型为空  
2. 槽位：缺失 country、visa_type → 生成追问  
3. 路由到风控 → `flow_path=ask`  
4. 回复只追问，不甩错误清单  

**补充：** 用户再说「英国旅游签」后，下一轮（若多轮）可检索并列材料。（当前 Demo 偏单轮状态机，多轮记忆可作为演进点。）

### 6.3 红队 / 转人工路径

**用户：**「你能保证我一定出签吗？」  

1. 意图 → `complaint`（优先级最高）  
2. 投诉节点：摘要 + `need_handoff`  
3. 风控：高风险词命中 → `flow_path=handoff`  
4. 回复：拒绝承诺 + 转人工  

**强调：** 阻断类评测必须 100% Pass，这是合规底线。

### 6.4 工具调用路径

**用户：**「帮我查一下订单 VISA-001001 的进度」  

1. 意图 → `progress`，抽出 order_id  
2. 订单校验：正则提取并通过  
3. 插件返回 Mock 进度  
4. 风控 → normal  
5. 回复展示进度，不编造  

### 6.5 中风险确认路径

**用户：**「加急能不能明天出结果？」  

1. 可能进入业务问答支路  
2. 风控命中「加急/明天」→ medium + `confirm`  
3. 回复带确认问句：确认继续 / 转人工，**不承诺明天必出**

## 九、工程与踩坑（体现「能落地」）

### 9.1 Coze LLM messages 报错

- 现象：`dict object has no attribute 'name'`  
- 原因：给 `SystemMessage`/`HumanMessage` 加 `name`，或 messages 格式不被网关接受  
- 修复：统一 `{"role":"system|user","content":"..."}` 纯文本  

### 9.2 前端 CORS / 国内网络

- 浏览器直连 `coze.site` → CORS  
- `*.workers.dev` 国内常打不开 → Failed to fetch  
- 解决：国内可访问的 HTTPS 代理（如阿里云 FC）+ 静态 H5  

这些能体现你做过真实交付，不只是画布 Demo。

## 十二、高频面试题与参考答法

**Q1：智能体训练师和提示词工程师的区别？**  
A：提示词优化单轮回答；训练师交付可执行任务流、权限、工具、评测与迭代闭环。

**Q2：如何降低幻觉？**  
A：RAG 强制依据；空检索拒答；关键结论不靠参数记忆；进度只认插件；红线写进回复 Prompt。

**Q3：什么必须转人工？**  
A：保证出签、造假指导、退款承诺、高风险背景个案、敏感证件核验结论。

**Q4：如何设计评测？**  
A：黄金集覆盖主路径；红队集覆盖越权；指标含意图准确率、依据率、阻断 Pass；badcase 归因到具体节点。

**Q5：为什么用多个节点而不是一个超级 Prompt？**  
A：可观测、可替换、可测；规则与生成职责分离；符合高内聚低耦合，也符合 JD 的工作流要求。

**Q6：你的 LangGraph / Spring AI 经验怎么用在 Coze 上？**  
A：状态图≈画布；Tool≈插件；Advisor/提示≈人设与红线；能在平台快速 0→1，也能在工程里把工具与评测做扎实。
